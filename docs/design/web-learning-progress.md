## 开发方案与验收标准（实施前）

保持一个主要结果“从真实进度回到正确学习任务”，按共享协议和存储顺序串行实施：

1. 聚合补充：保留正式复习来源；路线按不可变版本稳定排序，报告前版、
   新增/移除活动、当前版本及更新时间。完成步骤仍只来自明确推进事件，未知保持未知。
   附带原答案入口，复用 #31，模型建议、待确认、正式证据和手动完成独立显示。
2. 复习闭环：沿用原会话 `present_review`；原会话不可继续时明确说明原因，
   用户显式创建绑定原任务、来源证据和原 context 的承载会话。新题使用新活动及
   可校验引用，原任务、答案和证据不迁移、不复制；创建与重试走原事务/幂等屏障。
3. Web：`/app/progress` 的全局/区/目标、状态、截止时间、排序和分页全部传给服务端。
   首页先显示继续和待办，目标详情共用组件。查询键固定身份及范围，不拼接旧页；
   游标过期明确重置；默认复习截止时间沿用服务器冻结值。错误、延迟、重建、空与
   清除分开；投影失败仍可从正式答案记录读取历史。只在内存保存查询和重试身份。
4. 同步 OpenAPI、必要 CLI DTO 和使用文档；先失败回归，后受影响包、真实 PG
   投影增量/重放/隐私、浏览器和 CLI 读取，再类型检查、构建与 diff 检查。

退出标准：两区三目标入口准确；范围分页计数一致；同任务去重、不同目标独立；
动态分母说明版本且不等于能力；复习作答可由 API/CLI 读回并保留出处；新承载明确
发起且不改旧任务；暂停/归档/完成只影响可见和可执行性；丢响应和迟到不重复提交；
清除后旧投影和缓存不恢复正文。真实依赖缺失的检查如实记录，不能用 mock 冒充。

按工作项的明确落地边界在当前分支提交供审查，不合并、rebase 或推送基础分支。
