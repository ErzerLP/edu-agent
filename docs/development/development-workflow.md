# 项目开发工作流

## 目标

本工作流用于提高可交付吞吐量，同时保留项目对权威数据、隐私、幂等、重放和跨平台安全的要求。进度单位是一个可运行、可验证、可提交的用户结果，不是代码行、表数量、验收项数量或重复测试次数。

## 文档职责

`brief.md` 只记录结果、范围、非目标、关键决定和少量端到端验收示例。`spec.md` 描述 capability 归档后的完整可观察行为和必要不变量。`docs/design/` 保存协议字段、状态矩阵、迁移方案、文件格式和实施细节。`verification.md` 只由 Runtime 生成，不手工修改。

正式需求不得复制整份实现设计。只有影响兼容性、安全边界、数据所有权或用户可见语义的实现约束，才进入正式 spec。

## Change 大小与拆分

一个普通 change 应满足以下条件：

- 只有一个主要用户结果和一个主要端到端工作流。
- 可以由一个独立候选完成并验证，不依赖尚未确定的公共 API 或数据模型。
- 修改区域通常集中在一个 capability，跨模块修改是为该垂直结果服务。
- 正式验收项目标为 10 至 30 项，且每项描述一个可观察结果或必要不变量。

出现以下任一情况时必须执行拆分评估：

- 存在两个以上可以独立演示、发布或回退的用户结果。
- 同时建设协议、客户端存储、异步 worker、隐私清除和多平台适配等独立子系统。
- 预计需要超过 40 个正式验收项，或一个候选必须运行三个以上彼此独立的重型验证矩阵。
- 不同工作可以在不共享可变文件、schema 或公共接口的前提下独立实现。

超过 60 个正式验收项的 change 默认不得进入 Build。只有无法形成独立结果、拆分会破坏原子业务语义，并且用户明确确认单 change 理由时才可保留。

拆分优先使用 Supervisor Change 和依赖明确的 child。不能安全拆分工作区时，在同一 change 内定义有界垂直批次，但每个批次仍必须有独立退出标准。

## 垂直交付批次

每个 Build 批次必须同时包含完成该结果所需的最小领域、持久化、应用、transport、客户端和查询路径。不得长期只建设横向底层而没有可运行入口。

批次说明使用以下模板：

```text
结果：用户或调用方在批次结束后能做什么
范围：本批次允许修改的 capability 和接口
延期：明确留给后续批次的行为
退出标准：可运行场景、必须通过的最小检查、文档更新
重型证据：哪些检查延迟到候选，延迟原因是什么
```

一个批次只有在生产路径完整、受影响 package 通过、已知限制被记录且工作树可提交时才算完成。只有底层类型、表或 mock 的批次不算垂直完成，除非它是经确认的独立基础 child。

## 工作流阶段

### Shape

先调查仓库和运行环境，再确认用户可见结果、范围、非目标、数据所有权和验收标准。Shape 阶段完成拆分检测；不得把技术探索形成的所有边界情况都升级成正式验收项。

### Build

一次只推进一个明确批次。开始前记录结果、延期和退出标准；实现期间遵循最小测试反馈。批次完成后提交可审查状态，再开始下一个批次。

### Candidate

所有批次完成后重新核对完整 brief/spec。此时才运行全量候选门禁、生成 Builder handoff，并说明复用证据及其 evidence key。

### Verify

Verifier 必须独立读取需求和实现。稳定候选前不得派发宽范围审计；局部修复只重跑被修改输入影响的检查。验收失败返回 Build，用户可见需求变化返回 Shape。

### Archive

只有 Runtime 已接受验收结果时归档。归档不顺带提交无关工作区修改，也不把本地 Agent、会话或临时文件纳入版本控制。

## WIP 与并行

每个开发者或 Agent 同时只拥有一个 in-progress 写入批次。出现阻塞时先记录 blocker，再选择不修改相同接口、schema、配置或生成物的独立工作。

并行工作必须具有独立文件边界、独立验收和独立测试环境。共享 OpenAPI、migration、应用 composition、锁文件或公共 DTO 的工作默认串行。并行的目标是缩短关键路径，不是增加同时未完成的工作。

## 需求漂移

下列变化必须返回 Shape：

- 新增或删除用户可见命令、API、状态或错误语义。
- 改变数据所有权、隐私承诺、兼容性或验收标准。
- 将原定延期项纳入当前 change，或把当前承诺推迟到未来 change。
- 发现原 change 需要拆成新的用户可见交付结果。

普通实现选择、内部重构和不改变合同的测试补充保留在 Build。不得通过修改测试来绕过已确认需求，也不得在实现中隐式扩大正式范围。

## Definition of Ready

进入 Build 前必须满足：

- Outcome、Scope、Non-goals、Decisions 和验收项无 blocking 问题。
- 已完成拆分检测，并记录保持单 change 或 Supervisor 拆分的理由。
- 第一个垂直批次的结果、延期和退出标准明确。
- 已识别受影响的数据 owner、公共接口、migration 和重型测试环境。
- 当前工作区归属清楚，现有修改不会被覆盖或错误归因。

## Definition of Done

一个 change 完成必须满足：

- 所有已确认用户结果均存在可运行生产路径。
- 完整 brief/spec 与实现一致，没有仅存在于测试或设计文档中的承诺。
- 每个验收项有独立结论，必要检查成功，未运行项没有被表述为通过。
- 数据迁移、重放、隐私、幂等和降级语义按其风险完成验证。
- 文档、OpenAPI、CLI 帮助和运维说明与实现同步。
- 工作区无当前任务之外的暂存内容，Runtime 已进入允许归档的状态。

## 进度度量

优先记录以下指标：

- 从批次开始到首个端到端绿色场景的时间。
- 每个批次首次通过所需的实现和测试循环次数。
- 重型检查的复用率和无输入变化重跑次数。
- 需求返回 Shape、Verify 返回 Build 和无进展循环的原因。

不使用测试执行次数、验收项总数或新增代码量作为完成度指标。
